# DATABASE_CHOICES — คำตอบจากบทอ่านเพิ่มเติม (บทที่ 8)

## 1. ทำไมโปรเจกต์นี้เลือก SQLite แทน MongoDB

เพราะข้อมูลคำร้องของเรามี **โครงสร้างที่ชัดเจน** ทุกคำร้องต้องมี id, requesterName, requestType, location, details, priority, status เสมอ ลักษณะแบบนี้เหมาะกับ relational database ที่กำหนด schema ไว้ล่วงหน้าด้วย `CREATE TABLE` พร้อม `CHECK` constraint เพื่อบังคับว่าค่าต้องถูกต้อง

นอกจากนี้ข้อมูลยังมี **ความสัมพันธ์ระหว่างตาราง** คือ ผู้ใช้ 1 คนสร้างคำร้องได้หลายใบ (1-to-many) ที่แยกเป็นตาราง `users` กับ `requests` แล้วเชื่อมด้วย `FOREIGN KEY (requester_id) REFERENCES users(id)` ทำให้ไม่ต้องเก็บชื่อ-อีเมลซ้ำ ๆ ในทุกคำร้อง ถ้าใช้ MongoDB ที่เป็น NoSQL แบบ document จะไม่มี FOREIGN KEY มาบังคับ ข้อมูลอาจไม่สอดคล้องกันได้ เช่น ลบ user ไปแล้วแต่คำร้องยังอ้างถึง user ที่ไม่มีอยู่

## 2. ถ้าวันหนึ่งต้องเปลี่ยนไป MongoDB จะกระทบชั้นไหนบ้าง

กระทบ **2 ชั้น** คือ **service** และ **controller** 
เนื่องจาก MongoDB driver สำหรับ Node.js (ไม่ว่าจะเป็น `mongodb` หรือ `mongoose`) ออกแบบมาให้ทำงานแบบ async เนื่องจาก data base มักอยู่ **คนละเครื่องกับ API** ต้องสื่อสารผ่านเครือข่าย (เวลาไม่แน่นอน) เลยใช้ Promise เพื่อไม่ให้ server ค้างรอ ต่างจาก SQLite ที่เป็นไฟล์อยู่ในเครื่อง local อ่านเขียนเร็วจนใช้ sync ได้ชิลๆ

ดังนั้น service ทุกฟังก์ชันต้องเปลี่ยนเป็น `async` และ controller ก็ต้องเติม `await` ทุกจุดที่เรียก service ด้วย เช่น `const found = service.findById(id)` ต้องกลายเป็น `const found = await service.findById(id)` 

## 3. async จำเป็นเมื่อไร ไม่จำเป็นเมื่อไร

**จำเป็น** — เมื่อฐานข้อมูลอยู่ **คนละเครื่อง** กับ API (เช่น MongoDB Atlas, PostgreSQL cloud) เพราะต้องส่งข้อมูลผ่านเครือข่าย ซึ่งใช้เวลาไม่แน่นอน ถ้าใช้ sync server จะค้างรอจนกว่าจะได้คำตอบ ทำให้ คำสั่งถัดไปต้องรอด้วย

**ไม่จำเป็น** — เมื่อฐานข้อมูลอยู่ **ในเครื่องเดียวกัน(local)** (เช่น SQLite ที่เป็นไฟล์ `campus.db`) เพราะอ่านเขียนไฟล์ในเครื่องเร็วจน
