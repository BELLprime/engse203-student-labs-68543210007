## ครั้งที่ 1 · เปรียบเทียบ SQLite กับ MongoDB (สำหรับเขียน DATABASE_CHOICES.md - CP41)

**ถามอะไร**
- ต้องการเปรียบเทียบ SQLite กับ MongoDB ว่ามีความแตกต่างกันอย่างไร ทั้งในแง่แนวคิด รูปแบบข้อมูล ความซับซ้อน และการใช้งาน เพื่อนำไปสรุปตอบคำถามใน `DATABASE_CHOICES.md` ข้อที่ 1 และ 2

**AI ตอบว่าอย่างไร (สรุปสั้น)**
- ทั้งสองตัวเป็นระบบจัดเก็บข้อมูลเหมือนกัน แต่มีแนวคิดการออกแบบที่ต่างกันมาก:

| หัวข้อ | SQLite | MongoDB |
|---|---|---|
| **ประเภทฐานข้อมูล** | Relational Database (SQL) | NoSQL Document Database |
| **รูปแบบข้อมูล** | ตาราง (Table, Row, Column) มี Schema แน่นอน | เอกสาร JSON / BSON ยืดหยุ่น |
| **ภาษา Query** | SQL (`SELECT`, `INSERT`, `JOIN`) | MongoDB Query Language (`find()`, `insertOne()`) |
| **การติดตั้ง** | ไฟล์เดียวจบ (`campus.db`) ไม่ต้องมี Server | ต้องรัน MongoDB Server แยกต่างหาก |
| **ความซับซ้อน** | ง่าย เบา ใช้ `node:sqlite` ในตัวได้ทันที | ซับซ้อนกว่า ต้องจัดการ Driver และ Connection |
| **ความสัมพันธ์ (Relations)** | ดีมาก รองรับ `FOREIGN KEY` และ `JOIN` | ไม่เด่น เน้นเก็บเป็นฝังใน Document เดียวกัน |
| **ความยืดหยุ่น Schema** | ต้องกำหนดโครงสร้างล่วงหน้าด้วย `CREATE TABLE` | Schema-less เพิ่ม/ลด Field ได้อิสระ |
| **เหมาะกับ** | Mobile App, Desktop App, โปรเจกต์ขนาดเล็ก-กลาง | Web App ขนาดใหญ่, Big Data, Chat App |

**ตัวอย่างการจัดเก็บและดึงข้อมูล:**
* **SQLite:**
  ```sql
  -- ตาราง Users (Relational)
  SELECT * FROM users;
  ```
* **MongoDB:**
  ```javascript
  // Collection Users (Document JSON)
  db.users.find({ name: "Bell" });
  ```

**ข้อดี SQLite:**
* ✅ ไฟล์เดียวจบ ไม่ต้องติดตั้งฐานข้อมูลแยก
* ✅ ข้อมูลมีโครงสร้างชัดเจน และตรวจสอบความถูกต้องด้วย `CHECK` constraint ได้
* ✅ สอดคล้องกับความสัมพันธ์แบบ 1-to-many (ผู้ใช้ 1 คนสร้างคำร้องได้หลายใบ)

**ข้อดี MongoDB:**
* ✅ เก็บข้อมูลรูปแบบ JSON/Document ได้โดยตรง
* ✅ ขยายระบบออกหลายเครื่อง (Horizontal Scaling) ได้ง่าย

**ใช้ส่วนไหน / แก้เองตรงไหน**
- นำความเข้าใจนี้ไปเขียนเรียบเรียงเป็นคำตอบด้วยภาษาของตนเองในไฟล์ `DATABASE_CHOICES.md` โดยอ้างอิงจากโครงสร้างจริงของ `schema.sql` และวิเคราะห์ว่าทำไมโปรเจกต์นี้จึงเลือก SQLite แทน MongoDB

**เข้าใจโค้ดที่ได้มาไหม** ☑ เข้าใจทั้งหมด ☐ เข้าใจบางส่วน ☐ ยังไม่เข้าใจ

## ครั้งที่ 2 · ทำความเข้าใจการทำงานของ `.get().c` ใน `requestService.js`

**ถามอะไร**
- สอบถามว่าโค้ด `const ready = db.prepare("SELECT COUNT(*) c FROM sqlite_master WHERE type='table' AND name='requests'").get().c;` ตัว `.get().c` คืออะไรและทำงานอย่างไร

**AI ตอบว่าอย่างไร (สรุปสั้น)**
- `.prepare(...)` คือการเตรียมคำสั่ง SQL
- `.get()` คือการรันคำสั่งเพื่อดึงผลลัพธ์แถวแรกออกมาในรูป Object เช่น `{ c: 1 }`
- `.c` คือการเข้าถึงค่าตัวเลขของคอลัมน์ชื่อ `c` ซึ่งเป็น Alias ของ `COUNT(*)` ที่เราตั้งไว้ใน SQL
- ใช้เพื่อตรวจสอบว่ามีตาราง `requests` อยู่แล้วหรือไม่ ถ้ายังไม่มี (`ready === 0`) โค้ดจะสั่งรัน `schema.sql` เพื่อสร้างตารางและใส่ข้อมูลตั้งต้นอัตโนมัติ

**ใช้ส่วนไหน / แก้เองตรงไหน**
- นำไปใช้ทำความเข้าใจการทำงานของฟังก์ชัน `loadSeed()` ใน `api/src/services/requestService.js` เพื่อให้อธิบายปากเปล่าและอธิบายในวิดีโอสาธิตได้ถูกต้อง

**เข้าใจโค้ดที่ได้มาไหม** ☑ เข้าใจทั้งหมด ☐ เข้าใจบางส่วน ☐ ยังไม่เข้าใจ

## ครั้งที่ 3 · การรันแบบ Single Port ใน Production และ CORS

**ถามอะไร**
- สอบถามว่าทำไมในโหมด Production ถึงเปิดแค่พอร์ต 3001 พอร์ตเดียวได้ และทำไมถึงไม่มีปัญหาเรื่อง CORS

**AI ตอบว่าอย่างไร (สรุปสั้น)**
- ใน `api/src/app.js` บรรทัดที่ 41–48 เมื่อ `NODE_ENV=production` เซิร์ฟเวอร์ Express จะทำหน้าที่เสิร์ฟไฟล์ static จาก `frontend/dist` ด้วย `express.static()` และดักทุก Route ที่ไม่ใช่ `/api` ให้ส่ง `index.html` กลับไป
