# DATA_MODEL.md — การออกแบบฐานข้อมูล Campus Service Request

เอกสารอธิบายโครงสร้างและการตัดสินใจออกแบบฐานข้อมูลสำหรับระบบ Campus Service Request (ENGSE203 สัปดาห์ที่ 9)

---

## 1. ภาพรวม

ระบบนี้ประกอบด้วย 2 ตารางหลัก คือ `users` (ผู้ใช้งาน) และ `requests` (คำร้องแจ้งซ่อม/บริการ)

```text
┌───────────────────────┐              ┌────────────────────────────────┐
│         users         │              │            requests            │
├───────────────────────┤              ├────────────────────────────────┤
│ PK  id (INTEGER)      │ 1 ──────── < │ PK  id (TEXT)                  │
│     name (TEXT)       │              │ FK  requester_id (INTEGER)     │
│     department (TEXT) │              │     request_type (TEXT)        │
│     email (TEXT)      │              │     location (TEXT)            │
└───────────────────────┘              │     details (TEXT)             │
                                       │     priority (TEXT)            │
                                       │     status (TEXT)              │
                                       │     created_at (TEXT)          │
                                       └────────────────────────────────┘
```

* **รูปแบบความสัมพันธ์:** เป็นความสัมพันธ์แบบ **หนึ่งต่อหลาย (One-to-Many / 1:N)**
* **คำอธิบาย:** ผู้ใช้งาน 1 คน (`users`) สามารถสร้างคำร้อง (`requests`) ได้หลายรายการ แต่คำร้องแต่ละรายการจะถูกส่งโดยผู้ใช้เพียงคนเดียวเท่านั้น โดยเชื่อมโยงผ่าน `requests.requester_id` ที่ชี้ไปหา `users.id`

## 2. ทำไมต้องแยกเป็น 2 ตาราง

### ถ้าสมชายเปลี่ยนชื่อ ต้องแก้กี่ที่?
* **ตอน Week 06–07 (ตารางเดียว/ไฟล์ JSON ก้อนเดียว):** เราเก็บชื่อผู้แจ้ง (`requesterName: "สมชาย ใจดี"`) แปะไว้ในทุกคำร้อง ถ้าสมชายเคยส่งคำร้องไว้ 5 ครั้ง แล้วสมชายมาขอเปลี่ยนชื่อ เราต้องตามไปไล่แก้ทั้ง 5 จุด ถ้าลืมแก้แม้แต่จุดเดียว ข้อมูลจะขัดแย้งกันทันที
* **ตอน Week 09 (แยก 2 ตาราง):** เราเข้าไปแก้แค่ **1 ที่เท่านั้น** คือที่แถวของสมชายในตาราง `users` (`UPDATE users SET name = '...' WHERE id = 1`) จากนั้นคำร้องทุกใบของสมชายเวลาดึงข้อมูลด้วย `JOIN` ก็จะแสดงชื่อใหม่ให้ทันทีโดยอัตโนมัติ

### 4 ปัญหาสำคัญจากการเก็บข้อมูลรวมไว้ในตารางเดียว
1. **ข้อมูลซ้ำซ้อน (Data Redundancy):** ถ้าผู้ใช้คนเดิมส่งคำร้อง 10 ครั้ง เราต้องเก็บชื่อ, ภาควิชา และอีเมลซ้ำกันถึง 10 รอบ ทำให้เปลืองพื้นที่จัดเก็บโดยไม่จำเป็น
2. **แก้ข้อมูลไม่ครบแล้วข้อมูลขัดแย้งกัน (Update Anomaly):** ถ้ามีการแก้ไขข้อมูลผู้ใช้ เช่น เปลี่ยนอีเมลหรือเปลี่ยนชื่อ แล้วอัปเดตไม่ครบทุกคำร้อง จะทำให้คำร้องเก่ากับคำร้องใหม่แสดงข้อมูลของคนคนเดียวกันไม่ตรงกัน
3. **เก็บข้อมูลผู้ใช้ล่วงหน้าไม่ได้ (Insertion Anomaly):** ถ้ามีนักศึกษาหรืออาจารย์เข้ามาใหม่ แต่เขายังไม่เคยแจ้งซ่อมอะไรเลย ระบบจะไม่มีที่ให้บันทึกข้อมูลของเขา เพราะโครงสร้างเดิมบังคับว่าต้องมีคำร้องก่อนถึงจะมีชื่อคนได้
4. **พิมพ์ชื่อผิดพลาดจนระบบสับสน (Data Inconsistency):** การให้กรอกชื่อเป็นข้อความอิสระทุกครั้ง เช่น คนหนึ่งพิมพ์ "สมชาย ใจดี" อีกคนพิมพ์ "สมชาย  ใจดี" (เคาะเว้นวรรค 2 ที) หรือสะกดผิด ระบบจะมองว่าเป็นคนละคนกัน ทำให้เวลานำข้อมูลไปนับสถิติจะได้ตัวเลขที่ผิดพลาด

## 3. รายละเอียดตาราง

### ตาราง `users` (ข้อมูลผู้ใช้งาน)

| คอลัมน์ | ชนิดข้อมูล | ข้อกำหนด (Constraint) | เหตุผลที่เลือกแบบนี้ |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | เป็นรหัสประจำตัวผู้ใช้ ให้ระบบรันตัวเลข 1, 2, 3... อัตโนมัติ เหมาะกับการใช้เป็น Surrogate Key ที่ค้นหาและ JOIN ได้เร็ว |
| `name` | TEXT | NOT NULL | ชื่อ-นามสกุลของผู้ใช้ จำเป็นต้องมีเสมอเพื่อระบุตัวตน ห้ามเป็นค่าว่าง |
| `department` | TEXT | NOT NULL | ภาควิชาหรือหน่วยงานที่สังกัด จำเป็นต้องมีเพื่อใช้คัดกรองและจัดกลุ่มสถิติ |
| `email` | TEXT | NOT NULL, UNIQUE | อีเมลสำหรับติดต่อและใช้ระบุตัวตน บังคับห้ามซ้ำกันเพื่อป้องกันการสร้างบัญชีซ้ำ |

### ตาราง `requests` (ข้อมูลคำร้อง)

| คอลัมน์ | ชนิดข้อมูล | ข้อกำหนด (Constraint) | เหตุผลที่เลือกแบบนี้ |
|---|---|---|---|
| `id` | TEXT | PRIMARY KEY | ใช้รหัสรูปแบบ `REQ-001` ซึ่งเป็น Business Key ที่มนุษย์อ่านเข้าใจง่าย นำไปใช้อ้างอิงเวลาติดตามงานได้สะดวก |
| `requester_id` | INTEGER | NOT NULL, REFERENCES users(id) | Foreign Key ชี้ไปยัง `users(id)` เพื่อบอกว่าใครเป็นคนแจ้ง และป้องกันไม่ให้มีคำร้องที่ไม่มีคนแจ้ง (Orphan Record) |
| `request_type` | TEXT | NOT NULL, CHECK (request_type IN ('แจ้งซ่อม', 'บริการบัญชีผู้ใช้', 'ขอใช้อุปกรณ์', 'อื่น ๆ')) | ประเภทของคำร้อง จำกัดให้เลือกได้เฉพาะ 4 หมวดที่กำหนด เพื่อความถูกต้องของข้อมูล |
| `location` | TEXT | NOT NULL | สถานที่เกิดปัญหา เช่น ห้องปฏิบัติการ ต้องระบุเสมอเพื่อให้เจ้าหน้าที่ไปหน้างานถูกจุด |
| `details` | TEXT | NOT NULL | รายละเอียดปัญหาที่พบ ต้องมีข้อความอธิบายเสมอ ห้ามปล่อยว่าง |
| `priority` | TEXT | NOT NULL DEFAULT 'normal', CHECK (priority IN ('normal', 'urgent')) | ระดับความเร่งด่วน กำหนดได้แค่ 'normal' หรือ 'urgent' ตั้งต้นเป็นปกติ เพื่อใช้จัดลำดับงาน |
| `status` | TEXT | NOT NULL DEFAULT 'pending', CHECK (status IN ('pending', 'in-progress', 'completed')) | สถานะคำร้อง จำกัดให้เป็นไปตาม Workflow ของระบบ ตั้งต้นเป็น 'pending' เมื่อสร้างใหม่ |
| `created_at` | TEXT | NOT NULL DEFAULT (datetime('now', 'localtime')) | เวลาที่บันทึกคำร้อง ให้ฐานข้อมูลลงเวลาปัจจุบันให้อัตโนมัติ ใช้เรียงลำดับและดูประวัติ |

## 4. เหตุผลของการเลือกชนิดข้อมูลและข้อกำหนด

### 1. ทำไม `users.id` (INTEGER) กับ `requests.id` (TEXT) ถึงใช้ชนิดต่างกัน?
* **`users.id` เป็นตัวเลข (INTEGER AUTOINCREMENT):** เพราะเป็น Surrogate Key ภายในระบบ ออกแบบมาเพื่อให้ฐานข้อมูลจัดการรันลำดับเอง ตัวเลขจำนวนเต็มกินพื้นที่น้อย ประมวลผลและนำไปใช้ทำ Index สำหรับ `JOIN` ได้เร็วที่สุด
* **`requests.id` เป็นข้อความ (TEXT):** เพราะเป็น Natural Key / Business Key ที่ผู้ใช้งานและช่างต้องมองเห็นและนำไปใช้อ้างอิงจริง เช่น เวลาโทรศัพท์สอบถามสถานะจะบอกว่า "ตามใบงาน REQ-001" ซึ่งการมีคำนำหน้า `REQ-` ช่วยสื่อความหมายชัดเจนและป้องกันความสับสนกับรหัสเอกสารประเภทอื่น

### 2. ทำไมต้องมี CHECK constraint ทั้งที่ API ฝั่ง Express ก็ตรวจข้อมูลอยู่แล้ว?
* **ใช้หลักการ Defense in Depth (การป้องกันหลายชั้น):** เราไม่ควรฝากความปลอดภัยของข้อมูลไว้ที่ API เพียงด่านเดียว เพราะในโลกความเป็นจริง ข้อมูลสามารถถูกเพิ่มหรือแก้ไขผ่านช่องทางอื่นได้ เช่น การเปิดเข้าไปแก้ตรง ๆ ผ่านโปรแกรม Database Client, การรัน Migration Script หรือในอนาคตอาจมี Service อื่นเชื่อมเข้ามาใช้ฐานข้อมูลร่วมกัน
* การมี `CHECK constraint` อยู่ที่ตัวฐานข้อมูลโดยตรง จะทำหน้าที่เป็นปราการด่านสุดท้ายที่รับประกันว่า ข้อมูลที่บันทึกอยู่บนดิสก์จะถูกต้องและตรงตามกฎทางธุรกิจ (Business Rules) เสมอ 100%

## 5. ตัวอย่างการใช้ JOIN

คำสั่งดึงข้อมูลคำร้องพร้อมชื่อผู้แจ้งและสถานะ:

```sql
SELECT 
  r.id,
  u.name AS requester_name,
  r.request_type,
  r.location,
  r.status
FROM requests r
JOIN users u ON r.requester_id = u.id
ORDER BY r.id;
```

**ผลลัพธ์ที่ได้:**

| id | requester_name | request_type | location | status |
|---|---|---|---|---|
| REQ-001 | สมชาย ใจดี | แจ้งซ่อม | ห้องปฏิบัติการ 301 | pending |
| REQ-002 | สุภาวดี รักเรียน | บริการบัญชีผู้ใช้ | อาคารวิศวกรรม | in-progress |
| REQ-003 | ธนกฤต ตั้งใจ | ขอใช้อุปกรณ์ | ห้องประชุม 2 | completed |
| REQ-004 | สมชาย ใจดี | แจ้งซ่อม | ห้องปฏิบัติการ 302 | pending |
| REQ-005 | ปรียา ขยันยิ่ง | อื่น ๆ | ห้องสมุด ชั้น 2 | pending |

## 6. ข้อสังเกตสำหรับสัปดาห์ที่ 10

เมื่อเปรียบเทียบผลลัพธ์ที่ได้จากการ `JOIN` กับข้อมูลที่ Express API ส่งกลับไปให้ React ใน Week 07:

```text
-- ผลลัพธ์จาก SQL JOIN (Week 09)
REQ-001 | สมชาย ใจดี | pending

-- ข้อมูล JSON ที่ API ส่งให้ React (Week 07)
{ "id": "REQ-001", "requesterName": "สมชาย ใจดี", "status": "pending" }
```

**สิ่งที่สังเกตเห็น:**
* โครงสร้างข้อมูลที่ได้จากการ `JOIN` ระหว่างตาราง `requests` กับ `users` มีฟิลด์ตรงกับ JSON Object ที่ฝั่งหน้าเว็บ React รอรับพอดี
* แสดงว่าใน **Week 10** เมื่อเรานำ SQLite เข้ามาแทนที่การอ่าน/เขียนไฟล์ JSON สิ่งที่เราต้องทำมีเพียงแค่:
  - แก้ไขในไฟล์ `requestService.js` ไฟล์เดียว โดยเปลี่ยนจากการอ่าน Array/JSON มาเป็นการรันคำสั่ง `SELECT ... JOIN ...`
  - ส่วนของ Controller, Route และหน้าเว็บ React **ไม่ต้องแก้ไขโค้ดเลยแม้แต่บรรทัดเดียว** เพราะรูปแบบข้อมูลที่ส่งออกไปทาง HTTP ยังคงเหมือนเดิมทุกประการ

## 7. ผลการทดสอบ Constraint (CP25)

บันทึกการทดสอบข้อกำหนดความปลอดภัยของฐานข้อมูลทั้ง 5 รูปแบบ:

### ① Foreign Key Constraint
* **คำสั่งที่ทดสอบ:**
  ```sql
  INSERT INTO requests (id, requester_id, request_type, location, details)
  VALUES ('REQ-TEST-FK', 99999, 'แจ้งซ่อม', 'ห้องทดสอบ', 'ทดสอบ Foreign Key');
  ```
* **ผลลัพธ์:** `FOREIGN KEY constraint failed` (ถูกปฏิเสธสำเร็จ เนื่องจากไม่มี `users.id = 99999`)

### ② Check Constraint
* **คำสั่งที่ทดสอบ:**
  ```sql
  INSERT INTO requests (id, requester_id, request_type, location, details, status)
  VALUES ('REQ-TEST-CK', 1, 'แจ้งซ่อม', 'ห้องทดสอบ', 'ทดสอบ Check', 'ยกเลิก');
  ```
* **ผลลัพธ์:** `CHECK constraint failed` (ถูกปฏิเสธสำเร็จ เนื่องจากสถานะต้องเป็น 'pending', 'in-progress' หรือ 'completed' เท่านั้น)

### ③ Unique Constraint
* **คำสั่งที่ทดสอบ:**
  ```sql
  INSERT INTO users (name, department, email)
  VALUES ('สมชาย อีกคน', 'วิศวกรรมซอฟต์แวร์', 'somchai@rmutl.ac.th');
  ```
* **ผลลัพธ์:** `UNIQUE constraint failed: users.email` (ถูกปฏิเสธสำเร็จ เนื่องจากอีเมลนี้มีอยู่ในระบบแล้ว)

### ④ Primary Key / Unique ID
* **คำสั่งที่ทดสอบ:**
  ```sql
  INSERT INTO requests (id, requester_id, request_type, location, details)
  VALUES ('REQ-001', 1, 'แจ้งซ่อม', 'ห้องทดสอบ', 'ทดสอบ ID ซ้ำ');
  ```
* **ผลลัพธ์:** `UNIQUE constraint failed: requests.id` (ถูกปฏิเสธสำเร็จ เนื่องจากรหัส 'REQ-001' มีอยู่แล้ว)

### ⑤ Not Null Constraint
* **คำสั่งที่ทดสอบ:**
  ```sql
  INSERT INTO requests (id, requester_id, request_type, details)
  VALUES ('REQ-TEST-NN', 1, 'แจ้งซ่อม', 'ทดสอบลืมใส่ location');
  ```
* **ผลลัพธ์:** `NOT NULL constraint failed: requests.location` (ถูกปฏิเสธสำเร็จ เนื่องจากไม่ได้ระบุ `location`)
