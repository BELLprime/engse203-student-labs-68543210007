# รายงานผลการทดสอบความปลอดภัย — SQL Injection (CP31)

**วิชา:** ENGSE203 การพัฒนาซอฟต์แวร์ประยุกต์สำหรับองค์กร  
**สัปดาห์ที่ 10:** การบูรณาการฐานข้อมูล SQLite เข้ากับ Node.js / Express API  
**ผู้จัดทำ:** ณัฐกิตติ์ รอดเรือน (รหัสนักศึกษา: 68543210007-9, Sec 1)  

---

## 1. วัตถุประสงค์
เพื่อทดสอบและพิสูจน์ว่า Express API ที่เชื่อมต่อกับฐานข้อมูล SQLite (`campus.db`) มีการป้องกันการโจมตีประเภท SQL Injection อย่างสมบูรณ์ ตามมาตรฐานความปลอดภัยด้วยการใช้ Parameterized Queries (`?` placeholder)

---

## 2. ผลการทดสอบ 3 รูปแบบ

### ① เงื่อนไขที่เป็นจริงเสมอ (Always True Attack)
* **เป้าหมาย:** พยายามทำให้คำสั่ง SQL คืนค่าข้อมูลทั้งหมดออกมา โดยหลอกเงื่อนไข Boolean logic
* **คำสั่งที่ยิง:**
  ```bash
  curl "http://localhost:3001/api/requests?status=x'%20OR%20'1'='1"
  ```
* **ผลลัพธ์ที่ได้:** `[]` (0 รายการ, HTTP 200 OK)
* **การประเมิน:** ✓ **ปลอดภัย** (ไม่หลุดข้อมูลทั้งหมด)
* **เหตุผลทางเทคนิค:** โค้ดใน `requestService.js` ใช้ `db.prepare('... WHERE r.status = ?').all(status)` ตัวไดรเวอร์ `node:sqlite` ส่งค่า `x' OR '1'='1` เข้าไปในฐานะข้อความ literal ไม่ได้แทรกเข้าไปในไวยากรณ์ของ SQL

---

### ② พยายามลบตาราง (Stacked Query / DROP TABLE Attack)
* **เป้าหมาย:** พยายามปิดคำสั่งเดิมด้วย `;` แล้วรันคำสั่งทำลายล้างเพื่อลบตาราง `requests`
* **คำสั่งที่ยิง:**
  ```bash
  curl "http://localhost:3001/api/requests?status='%3B%20DROP%20TABLE%20requests%3B%20--"
  ```
* **ผลลัพธ์ที่ได้:** `[]` (0 รายการ, HTTP 200 OK)
* **การประเมิน:** ✓ **ปลอดภัย** (ตารางไม่ถูกลบ)
* **เหตุผลทางเทคนิค:** เครื่องหมาย `;` และคำสั่ง `DROP TABLE` ถูกมองเป็นเพียงตัวอักษรธรรมดาภายในสตริงค่าค้นหา `status` และ SQLite ไม่ยอมรับ stacked queries ผ่าน placeholder ตัวเดียว

---

### ③ ต่อเงื่อนไขเพิ่ม (Extra Condition Attack)
* **เป้าหมาย:** พยายามดึงข้อมูลสถานะอื่นเพิ่มเติมโดยการต่อ `OR` ใน query parameter
* **คำสั่งที่ยิง:**
  ```bash
  curl "http://localhost:3001/api/requests?status=pending'%20OR%20status='completed"
  ```
* **ผลลัพธ์ที่ได้:** `[]` (0 รายการ, HTTP 200 OK)
* **การประเมิน:** ✓ **ปลอดภัย** (ไม่หลุดข้อมูลสถานะ `completed` ออกมา)
* **เหตุผลทางเทคนิค:** ระบบค้นหาแถวที่มีค่า `status` ตรงกับสตริง `"pending' OR status='completed"` แบบตรงตัวทุกตัวอักษร ซึ่งไม่มีข้อมูลนี้ในฐานข้อมูล จึงได้ 0 รายการ

---

## 3. พิสูจน์สถานะของฐานข้อมูลหลังการทดสอบ

* **คำสั่งที่ทดสอบ:**
  ```bash
  curl http://localhost:3001/api/requests
  ```
* **ผลลัพธ์ที่ได้:** ได้รับรายการคำร้องทั้งหมดตามปกติ (HTTP 200 OK)
* **สรุป:** ฐานข้อมูลและตาราง `requests` ยังคงมีอยู่สมบูรณ์ ไม่ได้รับความเสียหายจากการโจมตีใดๆ
